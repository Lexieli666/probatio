# docs/DESIGN.md — rationale for non-obvious choices

One paragraph per choice, each naming the alternative it rejects. Ordered by the phase that made
the choice.

## Phase 0

**The version lives in `src/probatio/__init__.py`, not in `pyproject.toml`.** `pyproject.toml`
declares `dynamic = ["version"]` and points hatchling at the module attribute, so
`probatio.__version__` and the distribution metadata cannot drift apart. The rejected alternative
is a literal `version = "0.1.0.dev0"` in `pyproject.toml` plus a duplicate constant in the package,
which is the arrangement that produces a release whose installed metadata disagrees with what the
package reports at runtime. The smoke test asserts the constant, so a bump that forgets the module
fails the gate rather than shipping.

**The plugin module is loaded by every host suite, so it stays inert until it has work to do.**
Declaring the `pytest11` entry point in Phase 0 means `probatio.plugin` is imported by pytest in
every project that installs Probatio, including projects that never write an `LLMCase`. The module
therefore carries no imports beyond the standard library, registers no options and has no
import-time side effects; later phases add hooks that guard on the plugin's own flags. The rejected
alternative is deferring the entry point until Phase 9, when the hooks exist, which would leave the
declared console script and the declared plugin out of step with the packaging metadata for nine
phases and hide entry-point resolution bugs until late.

**Coverage is measured on `src/probatio` by path, not on the installed package.** The
`[tool.coverage.run]` section sets `source = ["src/probatio"]`, so a module that no test imports
is reported at 0% and drags the number down, instead of being silently absent from the report.
The rejected alternative, `source = ["probatio"]`, resolves through the editable install and
measures only what was imported, which reports a suite that never touches a module as fully
covered.

## Phase 1

**The demo suite's fake app matches one case-sensitive keyword per case, because a robust fake
would report nothing.** `examples/demo_suite/conftest.py` wires a `FakeProvider` whose responses
are keyed by a single token drawn from each case's prompt, and `tests/test_demo_spec.py` asserts
that every keyword occurs in exactly one case's prompt and in no distractor. That makes the fake
app brittle in a specific, legible way: permuting the documents and inserting an unrelated document
leave the keyword untouched, so `order_invariant` and `distractor_robust` report no violations,
while upper-casing the first sentence destroys the keyword whenever it sits there, so
`format_jitter` violates on most cases and not on the two whose keyword sits in a second sentence,
and the one hand-written paraphrase that avoids the word violates `paraphrase_invariant`. The
rejected alternative is a fake that answers correctly under every transformation — a dictionary
keyed by case id, say. It is easier to write and it is what a first draft reaches for, but it makes
every violation rate exactly zero, so the demo would show the headline feature reporting nothing
and no reader could tell a working relation from one that silently generates no variants. A demo
that cannot fail does not demonstrate a test tool.

**The byte-identity gate resolves its own baseline at test time rather than hard-coding a commit.**
`tests/test_demo_spec.py` runs `git log --diff-filter=A --format=%H -- examples/demo_suite` and
takes the last line, so the test knows which commit introduced the directory without a constant
that a rebase or an amended commit would invalidate; it then compares that commit with the
working tree using `git diff --quiet <commit> -- examples/demo_suite`, alongside
`git status --porcelain` for untracked files (Phase 2 corrected both, `DECISIONS.md` entry 17).
`git diff` sees tracked files only, so the `__pycache__` directories pytest leaves in the example
are irrelevant. When git is unavailable, or before the directory is committed at all, the test
prints a note and passes, which is what lets it be written in the same commit it guards. The rejected alternative is a checked-in manifest of file hashes: it would work
without git, but it has to be regenerated by hand, and a manifest regenerated in the same commit as
an illicit edit proves nothing.

## Phase 2

**The case model declares the assertion vocabulary; nothing in it evaluates an assertion.**
`case.py` defines the five assertion types as a pydantic discriminated union on `type` and stops
there: no similarity backend, no judge, no provider is imported. The consequence is that
`load_cases` can reject a typo in a rubric name's *field* at load time while knowing nothing about
rubrics, and that the module a user reads to learn the YAML format is the module that defines it,
in about a screen. The rejected alternative is one class per assertion carrying both its YAML
fields and its `evaluate()` method, which reads well in isolation and then forces `case.py` to
import the judge, the backends registry and the provider protocol, so that loading a case file
pulls in everything and a circular import appears the first time an assertion needs the case model
it was declared in.

**Cases are frozen, and `with_field` returns a validated copy rather than mutating.** A
metamorphic relation exists to produce variants of a case, and the cases it works on are shared:
`load_cases` is called once at module import and the same objects are parametrised into several
test functions. A relation that edited `case.input["documents"]` in place would silently change
what its neighbours are about to run, and under `--runs N` it would change what the *same* case
runs on its second pass. So `LLMCase` sets `frozen=True`, `with_field` deep-copies, replaces and
re-validates through `LLMCase.model_validate`, and it refuses to create a key that was not there.
The rejected alternative is `model_copy(update=...)`, which is faster and skips validation, so a
relation could produce a variant that the loader would have rejected — a case id that is not path
safe, say — and the failure would surface later as a bad baseline filename rather than at the line
that caused it.

**`Provider` is a `Protocol`, and an unknown cost is `None`, never `0.0`.** A user adding an
adapter for their own gateway should not have to import anything from Probatio, so the contract is
structural: a `name` attribute and a `complete(prompt, *, system, **params)` method. The other half
of the contract is that `Completion` is honest about ignorance — `tokens_in`, `tokens_out` and
`cost_usd` are `None` when the provider does not report them. The rejected alternative is
defaulting `cost_usd` to `0.0`, which is what makes a spreadsheet add up and what silently turns
every `max_cost_usd` ceiling into a check that can never fail; spec §3.7's unenforceable rule only
works because the absence of a price is representable.

**The fake provider is a three-layer lookup with a deliberately ugly fallback.** A response is
found by exact call key, then by prompt substring, then by a default that may be a callable, and
failing all three by `FAKE(<hash of the prompt>)`. The layers are what let one class serve three
jobs: replaying a recorded interaction keyed by its hash, standing in for an app that answers by
keyword, and grading as a judge that inspects the prompt it was handed. The fallback is
deliberately not a plausible sentence: the demo suite's judge fixture detects `FAKE(` and fails the
case, so a keyword table that stops matching shows up as a failing assertion instead of as a
suspiciously well-behaved run. The rejected alternative is raising when nothing matches, which
sounds stricter but makes it impossible to write a fake that answers most prompts one way and
anything unexpected another, and turns the interesting failure (the app changed, so the keyword no
longer appears) into a `KeyError` traceback with no case attached.

**Every flag of the Claude CLI adapter is a constructor argument.** The adapter shells out to a
program Probatio does not own and cannot version-pin, on a machine where the user may have any
release installed. So `-p`, `--output-format json`, `--model`, `--system-prompt`, `--tools ""` and
`--no-session-persistence` are defaults of named parameters, not literals in a list, and the
executable and timeout are too. When the CLI renames something, a user overrides one argument in
one line and keeps recording tapes; they do not wait for a Probatio release, and they do not fork
the adapter. The rejected alternative is hard-coding the argument vector, which is shorter and
reads better right up to the first rename, at which point every user of the adapter is blocked on
somebody else's release cycle.

## Phase 3

**Assertions return results; they never raise.** The pytest-native thing to do would be to write
`assert needle in output`, get the rewritten-assertion output for free, and stop at the first
failure. Probatio does the opposite: every evaluator returns an `AssertionResult` and
`evaluate_case` runs all of them. The reason is what an LLM regression looks like. A prompt change
does not break one thing; it breaks a case's schema *and* drops a required substring *and* moves
its similarity below the floor, and those three facts together say "the model started answering in
prose" while the first one alone says "line 41". The cost is that Probatio has to render its own
failure text instead of inheriting pytest's, which is why every result carries a `detail` written
to be read in a table. The rejected alternative is raising on the first failure and letting pytest
format it, which is less code and strictly less information per run.

**The default similarity backend is character trigrams with no padding, and it is deliberately
stupid.** The hard constraint is that a `pytest` run downloads nothing and gives the same number on
every machine, which rules out embeddings by default. Among the things that fit, character
trigrams over the whole normalised string — across word boundaries, not per token — degrade
gracefully in exactly the way this job needs: a clause that moves keeps almost all of its
trigrams, so a reordered sentence scores 0.923 where token-set overlap would score 1.0 and lose
the distinction, and a stem that changes keeps most of them, so `started`/`starting` does not fall
off a cliff. The rejected alternative is token Jaccard or a bag-of-words cosine, which is simpler
to explain but blind to morphology and to everything below the word, and which scores a genuine
paraphrase and an unrelated sentence about the same drug closer together than trigrams do.
`docs/assertions.md` publishes the five-pair table rather than describing this in prose, because
the only useful thing to tell a user picking `tau` is where the numbers actually land.

**`docs/assertions.md`'s table is parsed by a test, not duplicated in one.** The obvious way to
keep a documented number honest is to write the pairs in a test and assert the values, then paste
them into the doc. That keeps the *code* honest and lets the *doc* drift, which is the direction
that matters, since nobody re-reads a doc to check it. So `tests/test_docs_assertions.py` reads
`docs/assertions.md`, parses the markdown table, and recomputes each row with the shipped backend;
editing a score in the doc fails the suite. The rejected alternative is generating the table into
the doc from a script, which cannot drift either but puts a build step between a contributor and a
documentation edit, and leaves the committed file looking like something you should not touch.

**A judge with no provider is unenforceable, not skipped.** The tempting move for an assertion
that cannot run is `pytest.skip`, which is visible, standard and does not fail the build. It is
also how a suite ends up green while the only assertion that checks whether answers are *true* has
not run for a month. So `AssertionResult.unenforceable` is a third state: never a pass, counted
separately from ordinary failures, and listed under warnings with the number of judge verdicts
that did not happen. It is the same mechanism as spec §3.7's unenforceable cost ceiling, and it
exists for the same reason — an absent check has to be representable, or it is indistinguishable
from a passing one. The rejected alternative is skipping, which hides the gap in a count that CI
prints in grey and nobody reads.
